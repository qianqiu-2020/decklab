## USB 发现依据

准备前，BMC 的 `/sys/bus/usb/devices/1-8.3` 未出现。
使用 BMC 的单板 firmware-update 接口让 sub23-1 进入下载模式，收到成功回执后，
在同一物理路径识别 K3 BootROM（SPA3609）。没有修改设备序列号来绕过探测。
加载临时 FSBL、U-Boot 时设备重枚举，USB 地址发生变化；任务始终固定物理路径，
权限辅助进程只允许当前对应 USB 节点，不开放其他开发板或 UART。

## 现场发现与修复

第一次准备任务 `51703130ae989e685db7979a` 已完整备份，但预览错误要求旧的
设备端校验变量，未识别已证明的 RAM NOR 读取能力；等待选区超时，未写存储。
执行器修正必需校验的判断，并将外部单文件按 SHA-256 固定到受管理的计划缓存，
保持内容信息读取的目录边界。相应 Go 回归在 image-plan 和 live check-plan 前就设置 required。

第二次准备任务 `c29e9630f63a2dc6c50bbc97` 在预览阶段遇到单文件没有包目录时返回 JSON null，
Python 错将其直接迭代。修复后将 null 规范为空列表并增加真实 HTTP 回归；
原任务确认未写入后取消，保留备份，再停止并替换自己的临时后端。
两个失败准备都没有重放任何未知结果的写入。

测试驱动还修正了两个等待/选文件条件：以后端开始等待不代表浏览器已完成轮询，
以及后端已有多个文件时必须显式选择刚上传的文件。这两项不修改生产界面逻辑。

## 退出与归还

本轮不接管 UART，原 BMC 始终持有唯一 `/dev/ttyS51` 读者；临时后端的串口目录为空，
封闭设备权限只允许指定 USB 节点。结束时后端和 USB 权限辅助进程均停止，
临时程序、TLS 私钥及接入配置从 BMC 移除，私有任务数据库、备份与回执保留。
本机临时 Web 和源文件传输服务器也已停止。

原 spacemit_cluster、developer-serialbridge、cluster_cloud 的 PID 分别为
295982、1254960、579695，与测试前一致；原 prod.yaml SHA-256 仍为：

```text
59ff278224b0b48b58f625253662adc436151b9bb2fa194516363f22891946e9
```

归还时先断电 10 秒，原 +9 内核再次落入 initramfs；与此前该板 NVMe 间歇启动问题相同。
再次断电 30 秒后，原默认 `6.18.3+deb13+9-k3-uefi` 内核到达 Debian 13 的新登录提示。
没有刷写系统盘、替换内核、修改持久启动菜单、账户或 SSH 设置。启动恢复成功，根因未确认。
串口别名仍为 `/dev/ttyS_47 -> ttyS51`，原 BMC 主进程仅一个对应 UART 描述符。
