# 板卡控制适配验收

2026-11-14，1.9.0 候选代码。统一适配契约为 `ControlAction.bind(device)` →
`BoundControl.run(check, cleanup_failed)`；硬件任务负责授权、串口事务和持久记录。
新增 BMC HTTP 适配，旧固定命令仍通过 Linux 进程组或 Windows Job Object 执行。
没有把自动复位加入刷机准备、设备检测或配置保存。

## Linux BMC 实测

仅操作已指定的 sub23-1（BS01DCMA，模组 47，USB `1-8.3`），
使用候选代码的 BMC 适配进行登录、映射核对和单次控制请求。
串口观察订阅原 BMC WebSocket 数据流，不新增原始 UART 读者。

- `reset` 映射为 `ForceRestart`，收到成功回执；新串口输出进入原
  `6.18.3+deb13+9-k3-uefi` 内核，随后落入 initramfs。这验证复位动作发生，
  不代表正常系统启动成功；与此前该板间歇 NVMe 启动问题一致，根因未确认。
- 保存并检查原复位记录后，单独提交 `PowerOff`、等待 30 秒、再提交 `PowerOn`。
  两次控制请求均获确认，新输出 10,591 字节，原内核到达 Debian 13 登录提示。
  这次归还操作是显式新操作，没有重放丢失回执或未知结果的请求。
- 前后原 BMC 三个服务保持相同 PID：295982、1254960、579695；
  原配置 SHA-256 保持
  `59ff278224b0b48b58f625253662adc436151b9bb2fa194516363f22891946e9`，
  `/dev/ttyS_47 -> ttyS51` 不变。没有刷写、改动账户或持久启动配置。

原始意图、回执、新启动日志及服务核对记录位于本机私有
`dist/release-1.9.0/`；凭据和完整板卡日志不进入公开源码。
进入下载模式的 HTTP 映射有隔离回归；本轮未另外执行下载模式操作。
