# 云 BMC 单板后端真机验证

2026-11-14，在云 BMC 上以独立目录和临时进程运行 DeckLab 硬件后端，本机
Web 通过 HTTPS 连接。仅操作用户指定的 `sub23-1`：模组 47，
`/dev/ttyS_47 -> ttyS51`，USB 物理路径 `1-8.3`。

`1.7.5~web12`；刷机执行器为 `e6c370e75b42596ecbee24799b97c4a6dfc47f03`。
使用预备 RAM 材料 v6：FSBL SHA-256 为
`cfeeeee18728ef34a2d257311440a1bab8723cb554079de77dcf514d1b2bfdb0`，
U-Boot 为 `957cad315feffedd0b2fad15fe27f0266ee84adc6a7859ee244df42989f8b1a4`。

## BMC 影响与收尾

使用独立目录、单板 by-path 目录和封闭的设备访问权限。USB 重枚举时只更新
选定物理路径当前节点的权限。没有安装 deb、替换原服务或修改 prod.yaml。
原 BMC 的串口断开接口可能留下自动重连任务，因此临时持有该板串口别名，
先确认 BMC 主进程释放实际 UART，再启动 DeckLab 读者。结束时先停止新读者，
恢复原别名，再调用原单板重连接口并验证实时回传。

原 `spacemit_cluster`、`developer-serialbridge`、`cluster_cloud` 三个服务的
PID 和启动时间均与测试前一致；原配置 SHA-256 仍为
`59ff278224b0b48b58f625253662adc436151b9bb2fa194516363f22891946e9`。
临时后端、USB 权限辅助进程、Web 和传输服务器均已停止，临时程序与私有
接入配置已从 BMC 移除；两份 NOR 回读、日志、任务数据库及回执保留。

## 遇到的问题与范围

普通复位后曾落入 initramfs：+9 内核未枚举 NVMe 端点，根盘 UUID 为
`a96f51b4-f761-4eb2-82a0-3b3d61ca166f`。该板此前已有同内核、同 UUID 的
同类排障记录。总线重扫描、一次 PCIe 控制器重绑定、2 秒断电及一次性选择
板上 +8 内核未恢复；10 秒断电后，原默认 +9 内核恢复到登录界面。
本次未刷写系统盘、安装或替换内核，也未改写持久启动菜单。此结果仅证明恢复成功，
NVMe 间歇故障根因仍未确认，也未据此宣称已修复。

自动登录识别未通过，串口中出现 hvc0 与 ttyS0 两套登录提示及交错输入；
没有更改板端密码或 SSH 设置。临时加载器返回的缺省序列号没有用于建立正式
设备档案；操作绑定依靠已核验的 BMC 模组、UART 与固定 USB 路径。

本次覆盖 Ubuntu BMC 上一块 BS01DCMA 的串口和 NOR 单分区链路。
完整 NOR 恢复、GPT／eMMC／UFS 写入、SSH 登录及原生 Windows 硬件未在本轮验收。
原始证据位于本机 `dist/bmc-validation-20261113/`；其中私有接入文件和原始日志
不进入 Git，以上摘要与任务结果可用于复核。
