# 刷写耗时模型与参数选择

本文给出 DeckLab 系统盘刷写（普通刷写的写盘阶段与极速刷写）的耗时公式、实测参数和选型规则。条件变化（USB 速率、介质、芯片、主机）时，代入实测值即可算出合理配置。

## 写入方式回顾

板子先进入 DeckLab 临时 RAM U-Boot（BootROM → FSBL → U-Boot，不写板上固件），之后执行器按 1 MiB 扫描镜像：

- 整 1 MiB 全零、且连续不短于 32 MiB 的区段：不走 USB，由设备内存里一次清零的区域直接写盘（旧数据照样被覆盖，字节级一致）。
- 其余数据：首段 16 MiB、之后逐段翻倍到最多 256 MiB，主机 gzip 压缩 → Fastboot 下载 → 板上 `unzip` → `test ${filesize}` 校验长度 → 块写。每段按下式自动选择压缩或原样发送。
- 板上是单线程串行执行（下载、解压、写盘不能并行）；主机的下载、解包、压缩与板上流水并行，最多领先 2 段。

## 公式

记号（单位：字节、秒）：

| 变量 | 含义 | 获取方式 |
|---|---|---|
| `D` | 非零数据量（1 MiB 粒度） | 镜像扫描 |
| `Z` | 全零数据量 | 镜像扫描，`D + Z` = 分区写入总量 |
| `U` | Fastboot 下载有效速率 | 实测；USB 2.0 HS ≈ 43 MB/s |
| `r` | 压缩比（原始/压缩） | 与数据和级别有关 |
| `I` | 板上解压输出速率 | 实测，与芯片、编译选项有关 |
| `W` | 介质顺序写速率 | 实测 |
| `M` | 板上内存填充速率（`mw.l`） | 实测 |
| `c` | 每条 U-Boot 块命令的固定开销 | 实测 |
| `R` / `C` | 单段原始 / 压缩后字节数 | `r = R/C` |
| `v` | 每段解压后长度校验开销 | ≈ 0.03 s（一条命令往返） |
| `B` | 每段数据上限 | 256 MiB 且 ≤ `max-download-size`；首段 16 MiB，之后逐段翻倍 |
| `Zr` | 零区大小 | 256 MiB |
| `H` | 主机压缩聚合速率 | 与核数、级别有关 |
| `N` | 极速模式下载源包速率 | 网络 |
| `T_L` | BootROM 到 RAM U-Boot 可用 | 实测 |

**单段是否压缩**（每段独立判断，执行器运行中用实测 `U`、`I` 修正）：

```
压缩当且仅当   C/U + R/I + v  <  R/U
近似为         1/r + U/I < 1
```

`U/I` 是关键比值：USB 越快或板上解压越慢，越不值得压缩。

**总耗时**：

```
T ≈ T_L + T_0 + max(T_dev, T_host) + T_end

T_dev  = D·(1/(r·U) + 1/I + 1/W) + Z/W + Zr/M + n·c        （压缩段）
       = D·(1/U + 1/W)           + Z/W + Zr/M + n·c        （原样段）
n      ≈ 3·⌈D/B⌉ + ⌈Z/Zr⌉ + 若干（GPT、收尾）
T_host = max(源包大小/N, D/H)          普通刷写的 T_host 只算压缩（下载和准备在前面单独计时）
T_0    ≈ 首段准备时间 ≈ B0/H + B0/(r·U)，B0 = 16 MiB  （板子在等第一段）
T_end  ≈ 摘要核对 + 复位，约 0.5 s
```

**每字节板上成本**（用于比较编码与级别）：`k = 1/(r·U) + 1/I`，越小越好；原样发送时 `k = 1/U`。

**压缩级别**：在满足 `H(级别) ≥ 1.25 / (k + 1/W)`（主机不拖慢板子）的级别中取 `k` 最小者。执行器默认 gzip-6；若板子在某段上等待主机压缩超过 0.2 s，后续段降到 gzip-1。

**段大小**：`n·c` 随 `B` 变小而增大，`T_0` 随 `B` 增大。最优约 `B* ≈ sqrt(D·c / (1/H + 1/(r·U)))`，再受 `max-download-size` 和设备内存区限制。`c` 很小时（见下）`B` 对总时间影响不大。

## K3 实测参数（K3 开发板，NVMe，USB 2.0 HS 机位）

| 参数 | 数值 | 备注 |
|---|---|---|
| `U` | 42–43.5 MB/s | Fastboot 下载 200–512 MB 实测；`oem speed:super-speed` 在该机位无效（USB 2.0 hub） |
| `W`（NVMe） | 550–575 MB/s | 32 MiB 和 256 MiB 块写 |
| `c`（1.17.37 及以前的加载器） | 1.11 s | 每条 `nvme` 命令都重跑 `pci_init()`，空 PCIe 链路要等超时 |
| `c`（`CONFIG_PCI_INIT_R=y`） | 0.006 s | PCIe 只在启动时枚举一次 |
| `M` | 2.6 GB/s（`mw.l`） | `mw.b` 逐字节只有 0.29 GB/s，零区改用 `mw.l` 填充 |
| `T_L` | 10.0–10.4 s | FSBL 阶段 ≈ 7.0 s（其中 DDR 训练 ≈ 5.6 s），U-Boot 阶段 ≈ 2.8 s |
| `D` / `Z` | 1.25 GB / 1.43 GB | Bianbu-Minimal-UEFI-K3-20261119，三分区共 2.68 GB |
| `H`（gzip-6） | 约 250 MB/s | 控制机为 8 线程笔记本级 CPU，pgzip；板子等待主机累计 0.03 s |

板上解压（512 MB rootfs 样本）：

| 编码 | `r` | `I` -Os (MB/s) | `I` -O2 库 (MB/s) | `k` 用较快的 `I`（s/GB） | 说明 |
|---|---|---|---|---|---|
| 原样 | 1.00 | — | — | 23.0 | |
| gzip-6（`unzip`） | 2.66 | 262 | 256 | 12.5 | 当前默认，原生命令 |
| LZ4 HC（`unlz4`） | 2.40 | 314 | 317 | 12.8 | 原生 Kconfig，无收益 |
| zstd-3 | 2.93 | 206 | 280 | 11.4 | U-Boot 无现成命令，测试用 |
| zstd-9 | 3.10 | 216 | 290 | 10.9 | 同上 |
| zstd-19 | 3.45 | 181 | — | 12.2 | 主机压缩慢（16 线程约 17 MB/s） |

“-O2 库”指 `CONFIG_CC_OPTIMIZE_LIBS_FOR_SPEED=y`。整份 U-Boot 改为 `-O2` 对 `unzip`、`unlz4` 没有变化。

结论：USB 2.0 下 zstd-9 加 -O2 库比 gzip-6 每 GB 少约 1.6 s（本镜像约 2 s，6%），但 U-Boot 没有 zstd 内存解压命令，需要自带补丁。目前继续用原生 `unzip`。

## 实测核对（同板、同镜像，从 BootROM 起算）

| 方式 | 耗时 | 备注 |
|---|---|---|
| goflash 完整包（含 NOR） | 61.7 s | gzip 分段 + vendor `fb_blk` |
| goflash 仅系统盘 | 49.6 s | 包已在控制机解压好 |
| DeckLab 1.17.37 前普通刷写 | 785.9 s | 写盘阶段；8 MiB 分段，每段一次 PCIe 探测 |
| DeckLab 极速（1.17.38） | 32.8 s | 10.3 s 加载 + 22.5 s 边下载边写（含从网络下载 489 MB） |
| DeckLab 普通（1.17.38） | 10.2 s 加载 + 22.5 s 写盘 | 另需下载 4.2 s、准备镜像（有缓存时 0.9 s） |

极速模式写盘阶段拆分（`device_timing`）：USB 11.8 s、解压 5.0 s、写数据 2.2 s、写零 2.6 s，主机等待 0.03 s。代入公式：

```
D/(r·U) = 1.25 GB / (2.62 × 42.1 MB/s) = 11.3 s
D/I     = 1.25 GB / 249 MB/s         = 5.0 s
D/W     = 1.25 GB / 576 MB/s         = 2.2 s
Z/W     = 1.43 GB / 553 MB/s         = 2.6 s
```

与实测一致，误差主要是 GPT 写入和最后一段的流水排空。

## 再缩短的途径（K3、USB 2.0、本镜像）

| 途径 | 节省 | 代价 |
|---|---|---|
| 全零段改为不写（sparse DONT_CARE） | `Z/W` ≈ 2.6 s | 旧数据不再被覆盖，与 DeckLab 的逐字节写入语义不同；只能作为显式选项 |
| zstd-9 + -O2 库 | ≈ 2 s | 需要非上游的 U-Boot 命令（约 30 行，只调用现有 `lib/zstd`） |
| 跳过 DDR 训练 | ≈ 5.6 s | 需要 FSBL 复用已保存的训练结果，属于固件改动 |
| USB 3.0 SuperSpeed 接线 | ≈ 11 s | 取决于机位 hub；加载器需启用 SS |

在当前 USB 2.0 机位、坚持逐字节写入且不改固件时，下限约为 `T_L + D·k + (D+Z)/W` ≈ 10 + 16.3 + 4.8 ≈ 31 s。要降到 goflash 仅系统盘的一半（24.8 s），必须换 USB 3.0 接线，或者同时采用上表前三项。

## 其他条件下的推算

- **USB 3.0 SuperSpeed**（直连、加载器启用 SS）：`U` 约 300 MB/s 以上，`U/I > 1`，公式给出“全部原样发送”。K3 系统盘约 `T_L + D/U + (D+Z)/W` ≈ 10 + 4 + 4.8 ≈ 19 s，约为 goflash 仅系统盘的 40%。
- **主机较弱**（例如 4 线程笔记本，gzip-6 约 100 MB/s）：`H` 低于 `1.25/(k + 1/W)` ≈ 85 MB/s 时板子开始等主机。执行器检测到板子累计等待超过 1 s 后改用 gzip-1（主机快 3–4 倍，体积约大 10%）。
- **K1**（推断，待实板实测）：K1 走原厂 U-Boot 的 Fastboot `flash`，数据原样发送、零段用 sparse FILL，不经过上面的压缩通道，即 `T_dev ≈ D/U + (D+Z)/W`。若把压缩通道扩展到 K1：CPU 慢于 K3，`I` 预计 100–150 MB/s；USB 2.0 下 `U/I ≈ 0.3–0.4`，按公式仍应压缩，`k` 约 15–18 s/GB，比原样发送的 23 s/GB 少 25–35%。eMMC 顺序写 `W` 常见 60–150 MB/s，此时 `(D+Z)/W` 成为主项（2.7 GB 约 20–45 s），全零段的写入代价远高于 NVMe。若要再快，需要对零区使用 eMMC 擦除（按擦除组对齐、确认 `ERASED_MEM_CONT = 0`、仅用 ERASE 而非 DISCARD）——这一项尚未实现。
- **加载时间**：`T_L` 中 DDR 训练约 5.6 s，属于 FSBL 行为；复用板上已保存的训练结果需要固件配合，DeckLab 目前不改固件。

## 新条件下的测量方法

1. 极速刷写结果中的 `device_timing` 直接给出 `usb_mbps`、`inflate_mbps`、`write_mbps`、`zero_write_mbps` 和 `host_wait_s`。
2. 代入 `1/r + U/I < 1` 判断是否压缩；代入 `T_dev` 估算总时间。
3. `host_wait_s` 明显大于 0 说明主机压缩是瓶颈，应降低级别或换更强的控制机。
