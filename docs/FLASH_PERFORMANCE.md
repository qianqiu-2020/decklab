# 刷写耗时模型与参数选择

本文给出 DeckLab 系统盘刷写（普通刷写的写盘阶段与极速刷写）的耗时公式、实测参数和选型规则。条件变化（USB 速率、介质、芯片、主机）时，代入实测值即可算出合理配置。

## 写入方式

板子先进入 DeckLab 临时 RAM 环境：BootROM → FSBL → OpenSBI → U-Boot（S 模式），不写板上固件。之后执行器按 1 MiB 扫描镜像：

- 整 1 MiB 全零、且连续不短于 32 MiB 的区段不走 USB，由设备内存里一次清零的区域直接写盘。旧数据照样被覆盖，读回与镜像逐字节一致。
- 其余数据分段发送：首段 16 MiB，之后逐段翻倍，最多 128 MiB。主机把每段切成 4 MiB 的独立 zstd 帧，装进一个 DLZ1 容器；板上 `unzstd` 用全部空闲核并行解压，再用 `test ${filesize}` 核对长度。
- 解压结果在两块内存槽之间轮换。`bgblk` 在另一个核上写盘，主核同时接收下一段，下一次写盘前确认上一次的结果。
- 加载器没有 `unzstd` 时改用 gzip 与单核 `unzip`；没有 `bgblk` 时同步写盘。哪种方式都不划算时原样发送（见下式）。
- 主机的读盘或下载、解包、压缩与板上流水并行，最多领先 2 段。

## 公式

记号（单位：字节、秒）：

| 变量 | 含义 | 获取方式 |
|---|---|---|
| `D` | 非零数据量（1 MiB 粒度） | 镜像扫描 |
| `Z` | 全零数据量 | 镜像扫描，`D + Z` = 分区写入总量 |
| `U` | Fastboot 下载有效速率 | 实测；USB 2.0 HS ≈ 43 MB/s |
| `r` | 压缩比（原始/压缩） | 与数据、编码和级别有关 |
| `I` | 板上解压输出速率 | 实测；与芯片、核数、编码有关 |
| `W` | 介质顺序写速率 | 实测 |
| `c` | 每条 U-Boot 块命令的固定开销 | 实测 |
| `R` / `C` | 单段原始 / 压缩后字节数 | `r = R/C` |
| `v` | 每段解压后长度校验开销 | ≈ 0.03 s（一条命令往返） |
| `B` | 每段数据上限 | 128 MiB 且 ≤ `max-download-size`；首段 16 MiB，之后逐段翻倍 |
| `H` | 主机压缩聚合速率 | 与核数、级别有关 |
| `N` | 极速模式下载源包速率 | 网络 |
| `T_L` | BootROM 到 RAM U-Boot 可用 | 实测 |
| `o` | 写盘能否与下一段下载重叠 | 有 `bgblk` 为 1，否则为 0 |

**单段是否压缩**（每段独立判断，执行器运行中用实测 `U`、`I` 修正）：

```
压缩当且仅当   C/U + R/I + v  <  R/U
近似为         1/r + U/I < 1
```

`U/I` 是关键比值：USB 越快、板上解压越慢，越不值得压缩。

**总耗时**：

```
T ≈ T_L + T_0 + max(T_dev, T_host) + T_end

无重叠（o = 0）：
T_dev = D·(1/(r·U) + 1/I + 1/W) + Z/W + n·c

有重叠（o = 1）：每段的写盘与下一段的下载、解压同时进行
T_dev ≈ Σ_段 max(C_i/U + R_i/I, 上一段写盘 R_{i-1}/W) + 末段写盘 + n·c
      ≈ D·(1/(r·U) + 1/I) + max(0, Z/W − D/(r·U)) + B/W + n·c    （W ≫ r·U 时）

n      ≈ 4·⌈D/B⌉ + ⌈Z/256 MiB⌉ + 若干（GPT、收尾）
T_host = max(源包大小/N, D/H)       普通刷写只算压缩（下载和准备在前面单独计时）
T_0    ≈ B0/H + B0/(r·U)，B0 = 16 MiB   （板子在等第一段）
T_end  ≈ 摘要核对 + 复位，约 0.5 s
```

**每字节板上成本**（比较编码与级别）：`k = 1/(r·U) + 1/I`，越小越好；原样发送时 `k = 1/U`。

**压缩级别**：取 `max(板上耗时, 1.25/H)` 最小的编码与级别（见「实测生成刷写配置」）。没有实测配置时用 zstd 默认级别。刷写中板子累计等待控制机超过 1 s，改用最快级别。

**段大小**：`n·c` 随 `B` 变小而增大；`T_0` 和主机内存（约 `4·B` 加压缩缓冲）随 `B` 增大。`c` 只有几毫秒时，`B` 只需大到盖住写盘，并让主机内存保持在 1 GiB 左右，128 MiB 即可。

## K3 实测参数（K3 开发板，NVMe，USB 2.0 HS 机位）

| 参数 | 数值 | 备注 |
|---|---|---|
| `U` | 41–43.5 MB/s | Fastboot 下载 100–512 MB 实测；`oem speed:super-speed` 在该机位无效（USB 2.0 hub） |
| `W`（NVMe） | 550–575 MB/s | 128 MiB 和 256 MiB 块写 |
| `c`（1.17.37 及以前） | 1.11 s | 每条 `nvme` 命令都重跑 `pci_init()`，空 PCIe 链路要等超时 |
| `c`（`CONFIG_PCI_INIT_R=y`） | 0.006 s | PCIe 只在启动时枚举一次 |
| `T_L`（原 FSBL） | 10.0–10.4 s | FSBL 阶段 ≈ 7.0 s（其中 DDR 训练 ≈ 5.6 s），U-Boot 阶段 ≈ 2.8 s |
| `T_L`（1.17.39 FSBL） | 4.5–5.0 s | 复用板上保存的 DDR 训练结果，DDR 初始化 9 ms |
| `D` / `Z` | 1.25 GB / 1.43 GB | Bianbu-Minimal-UEFI-K3-20261119，三分区共 2.68 GB |
| `H`（zstd 默认级别） | 约 440 MB/s | 16 线程主机实测；8 线程笔记本级控制机上，板子等待主机累计 0.4–0.5 s |

U-Boot 中 PCIe 枚举约 1.1 s，花在没有设备的 PCIe-4 链路训练超时上，计入 `T_L`。

板上解压（K3，256–512 MB rootfs 样本）：

| 编码 | `r`（整镜像非零数据） | `I` (MB/s) | `k`（s/GB） | 说明 |
|---|---|---|---|---|
| 原样 | 1.00 | — | 23.3 | |
| gzip-6，单核 `unzip` | 2.45 | 250–262 | 13.3 | 原生命令；无 `unzstd` 时的回退 |
| LZ4 HC，单核 `unlz4` | 约 2.2 | 314 | 13.7 | 原生 Kconfig，无收益 |
| zstd-3，单核 | 2.76 | 206–280 | 12.0 | |
| zstd 默认级别，DLZ1，16 核 `unzstd` | 2.67 | 1150–2100 | 9.2 | 1.17.39 默认 |
| zstd 较高级别，DLZ1，16 核 | 2.89 | 约 2000 | 8.5 | 主机只有约 63 MB/s，不划算 |

单核 zstd 的 `I` 与 USB 同一量级，压缩省下的 USB 时间大半又花在解压上。16 核并行后 `U/I ≈ 0.03`，`k` 只剩 `1/(r·U)` 这一项。

## 实测核对（同板、同镜像，从 BootROM 起算）

| 方式 | 耗时 | 备注 |
|---|---|---|
| goflash 完整包（含 NOR） | 61.7 s | gzip 分段 + vendor `fb_blk` |
| goflash 仅系统盘 | 49.6 s | 包已在控制机解压好，不含下载 |
| DeckLab 1.17.37 前普通刷写 | 785.9 s | 仅写盘阶段 |
| DeckLab 极速（1.17.38） | 32.8 s | 10.3 s 加载 + 22.5 s 边下载边写 |
| DeckLab 极速（1.17.39） | 20.4–20.6 s | 4.6–5.0 s 加载 + 15.6–15.7 s 边下载边写（含从网络下载 489 MB） |
| DeckLab 普通（1.17.39） | 4.6–4.8 s 加载 + 15.8–16.3 s 写盘 | 另需下载约 4.3 s、准备镜像（有缓存时约 1 s） |

1.17.39 极速模式写盘阶段拆分（`device_timing`）：USB 下载 10.8 s，解压 1.0 s，等写盘 1.0 s，等零区写盘 1.2 s，等主机 0.4 s。代入公式：

```
D/(r·U) = 1.25 GB / (2.85 × 41.5 MB/s) = 10.6 s     # 实际压缩比 2.85（含 bootfs、ESP）
D/I     = 1.25 GB / 1200 MB/s          = 1.0 s
Z/W − D/(r·U) < 0                                      # 零区写盘被下载盖住
B/W + 首段 + 收尾                      ≈ 2–3 s
```

与实测一致。剩余时间几乎全是 USB 2.0 带宽。

## 再缩短的途径（K3、USB 2.0、本镜像）

| 途径 | 能省 | 代价 |
|---|---|---|
| USB 3.0 SuperSpeed 接线 | 约 9 s | 取决于机位 hub；见下面推算 |
| 去掉 U-Boot 对空 PCIe 口的链路等待 | 约 1.1 s | 需要按板型修改设备树或驱动超时 |
| 全零段改为不写（sparse DONT_CARE） | 约 1.2 s | 旧数据不再被覆盖，与逐字节写入语义不同，只能作为显式选项 |
| 更高 zstd 级别 | 约 0.7 s | 需要更强的控制机（`H` ≥ 约 140 MB/s） |

## 其他条件下的推算

- **USB 3.0 SuperSpeed**（直连、加载器启用 SS）：`U` 约 300 MB/s 以上。原样发送时 `k = 3.3 s/GB`，DLZ1 时 `k ≈ 1/(2.67·300 MB/s) + 1/1.2 GB/s ≈ 2.1 s/GB`，仍应压缩。此时写盘（`(D+Z)/W` ≈ 4.8 s）成为主项，K3 系统盘约 `T_L + max(D·k, (D+Z)/W)` ≈ 5 + 5 ≈ 10 s（推断）。
- **主机较弱**（例如 4 线程笔记本）：`H` 低于 `1.25/k` ≈ 140 MB/s 时板子开始等主机。执行器检测到板子累计等待超过 1 s 后改用最快级别（主机约快 2 倍，体积约大 4%）。
- **K1**：以下数据在 K1 开发板（8 核 X60 1.6 GHz，16 GB，eMMC）的 Linux 用户态测得；U-Boot 中的速率预计相近但未实测。

  | 参数 | 数值 |
  |---|---|
  | gzip-6 单核解压 | 52 MB/s |
  | zstd-3 单核解压 | 73 MB/s |
  | zstd-3 8 核并行（4 MiB 帧） | 247 MB/s |
  | eMMC 顺序写（直写） | 207 MB/s |
  | eMMC 顺序读 | 264 MB/s |

  代入公式（`U` = 43 MB/s）：
  - gzip：`1/r + U/I = 0.41 + 0.83 = 1.24 > 1`，压缩反而更慢；单核 zstd 同理（1.0）。
  - DLZ1 8 核：`1/2.67 + 43/247 = 0.55`，`k ≈ 12.8 s/GB`，原样发送是 23.3 s/GB。
  - 写盘：`(D+Z)/W` ≈ 2.68 GB / 207 MB/s ≈ 13 s。有 `bgblk` 时与下载重叠，否则要直接加上。

  因此 K1 的合理配置是：DLZ1 加 8 核解压、后台写盘；不要用单核 gzip。本镜像约 `T_L + D·k + 余量` ≈ T_L + 16 + 2 s（推断）。

  目前 K1 仍走原厂 U-Boot 的 Fastboot `flash`：原样发送，零段用 sparse FILL，`T_dev ≈ D/U + (D+Z)/W` ≈ 29 + 13 s（推断，未在 DeckLab 实测）。K1 版 `unzstd`/`bgblk` 和 K1 FSBL 复用训练数据尚未实现。
- **加载时间**：`T_L` 中 DDR 训练约 5.6 s。1.17.39 的 FSBL 在 USB 下载模式下复用板子自己保存在启动介质上的训练结果，并按正常启动的规则校验，不写板子。板上没有有效训练数据（例如 NOR 被擦除）时照常训练。若这一步后板子没有进入 U-Boot 下载阶段，DeckLab 会提示重新进入下载模式；在该 USB 口上，下一次改用每次都完整训练的原 FSBL。

## 实测生成刷写配置

公式中的参数可以在板上实测，测量结果保存为这块板的刷写配置，之后的刷写直接使用。

**怎么用**：在刷机面板展开「刷写配置」，点「实测并生成配置」。设备在 BootROM 时会先装入临时环境，整个过程约 10 秒（K3 实测 9.8 秒，其中装入 4.3 秒）。也可以调用 `POST /api/flash-calibrate`，见 [API](API.md)。

**测什么**（执行器 `calibrate` 操作）：

| 变量 | 测法 |
|---|---|
| `c` | 连续 5 条空命令（`test 1 = 1`）的平均往返时间 |
| `U` | 下载 64 MiB 样本 |
| `I`（gzip / zstd） | 下载压缩后的样本，计时 `unzip` / `unzstd`，并核对展开长度 |
| `r`、`H` | 控制机按各级别压缩样本，记录压缩比和压缩速度。样本是执行器自身二进制，与根文件系统一样以机器码为主 |
| 后台写盘 | 加载器是否支持 `bgblk`，且系统盘是 NVMe |
| `W` | 在系统盘中部读出 128 MiB，原样写回并计时，再读一次比对；盘上内容不变。可在面板取消勾选 |
| `T_L` | 若从 BootROM 开始，记录装入临时环境的耗时 |

板上存储的内容不受影响：载荷只进内存，写盘测速写回的是刚读出的同样字节。

**怎么选**：对每个编码和级别计算每 GB 非零数据的耗时，取最小者：

```
板上：  k = 1/(r·U) + 1/I            原样发送 k = 1/U
        有后台写盘 max(k, 1/W)，否则 k + 1/W
总计：  max(板上, 1.25/H)            1.25 给控制机留出下载、读盘和解包的余量
```

段大小取 128 MiB，并受设备 `max-download-size` 限制。

K3 云机位实测（8 线程控制机）：

| 编码 | 压缩比（样本） | 控制机压缩 | 板上 s/GB | 总计 s/GB |
|---|---|---|---|---|
| 原样 | 1 | — | 23.1 | 23.1 |
| gzip-6 | 2.28 | 326 MB/s | 16.1 | 16.1 |
| zstd 级别 1 | 2.20 | 610 MB/s | 11.5 | 11.5 |
| zstd 级别 2 | 2.31 | 352 MB/s | 11.0 | **11.0（选用）** |
| zstd 级别 3 | 2.36 | 98 MB/s | 10.8 | 12.7（控制机跟不上） |

同一配置下，极速刷写为 4.8 s 加载 + 15.8 s 写盘，普通刷写写盘阶段 15.6 s。

**存放与使用**：
- 配置按「芯片 + USB 口」保存在控制机刷机工作目录的 `tuning.json`，记录板子编号、测量时间、各项实测值和选择结果。
- 之后经同一 USB 口的普通刷写和极速刷写都带上这套配置；某个 USB 口没有自己的配置时，沿用同型号芯片最近一次实测。
- 配置只决定初始速率、编码、级别、段大小和是否后台写盘。刷写中执行器仍按实测速率调整，每段仍按真实压缩大小决定是否压缩，写入内容不变。
- 换线、换 hub、换控制机或换板后重新实测即可；面板可清除某个 USB 口的配置。
- 每次刷写的结果都记录 `flash_configuration`，说明用了哪套配置。

目前只支持 K3。K1 仍走原厂 U-Boot，没有 `unzstd`/`bgblk` 等加载器命令，暂不能实测。

## 新条件下的测量方法

1. 极速刷写结果中的 `device_timing` 直接给出 `codec`、`usb_mbps`、`inflate_mbps`、`download_s`、`inflate_s`、`write_wait_s`、`zero_write_wait_s`、`host_wait_s` 和 `background_writes`。
2. 代入 `1/r + U/I < 1` 判断是否压缩；按有无重叠选择 `T_dev` 公式估算总时间。
3. `host_wait_s` 明显大于 0，说明主机压缩是瓶颈，应降低级别或换更强的控制机。`write_wait_s` 明显大于 0，说明写盘没被下载盖住（介质慢，或 USB 快）。
